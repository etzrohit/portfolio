Cutting the time to release a change by 53% with Facets' new release flow

Part of the Facets platform rebuild

Facets is a tool companies use to set up and change the cloud servers and databases their apps run on.

With Facets, developers make these changes themselves, like giving an app more memory, instead of raising a ticket with the DevOps team and waiting. Every change goes live through the release flow, the most-used part of Facets.

TL;DR
Situation

Facets lets a company's engineers change their own cloud infrastructure, without waiting on a platform team. Every change reaches production through one flow, the release. Some companies release 4,000 times a month, and one wrong release can take their product down.

Problem

Engineers couldn't see what a release would change. In most releases, they left the flow to check each resource's settings, then came back to release. On the most-used flow in the product, every team paid that cost many times a day.

What I did

I redesigned the release around four things engineers need to know before they press Release: what's waiting, what will change, what's broken, and where it's going. A small fix shipped overnight, before the platform rebuild. The full redesign shipped with the rebuild.

Result

Releasing a change takes 53% less time (70s → 33s), and 1.1 passes through the flow instead of 2.3. Engineers see what will change before it goes live.

The shipped flow

Developers no longer leave the release to check their changes

The release now has two steps: choose resources, then review what will change. Reviewing is an extra step, but releasing still takes less time, because nobody leaves the flow to check.

Goal #01 · What's waiting

The resource list got the panel, filters and a Pending tab

  1. The environment: cloud, name, status and stage
  2. Release type: full, selective or custom
  3. All and Pending tabs, with counts
  4. A clock marks resources with pending changes
  5. Search, sort, and filters for type and status
  6. Settings and comments, folded into one line at the top

Dropped: open settings pushed the resource list, the main work, down the screen.

Dropped: release type is one simple choice. A screen of its own added a step before the real work.

Why this design
  • Choosing resources is the main work, so the list gets most of the panel. Settings stay on top, folded into one line, and open when needed. At the bottom, under a long table, they'd be out of sight.
  • Filters and a Pending tab replace typing names from lists kept in Slack.
  • The environment and release type stay in a narrow column beside the list, always in view.
Goal #02 · What will change

A review step shows what will change before anything runs

  1. Resources that will change, apart from those that won't
  2. The kind of change for each resource
  3. Old and new value, side by side
  4. Every choice from step 1, summarised

Dropped: one step would ask you to choose and check at the same time, and the list would grow long enough to need pages.

Why this design
  • People left the flow to check each resource's settings. The review step brings that check inside the flow.
  • A separate step does one job. Back returns to the list if something looks wrong.
  • Resources with no change sit on their own tab, so the ones that will change stand out. Compare opens the full difference.
Goal #03 · What's broken

One broken resource no longer stops the whole release

  1. A big warning card, below the release type

Dropped: a big card drew attention to warnings that people skipped anyway.

Before: the popup blocked every release with warnings, and 90% of the time people clicked Ignore & Proceed.

Why small, not big
  • Warnings stay small: 90% were dismissed, so people skipped them anyway, and a big card would only draw attention to them.
  • The label sits below the release type. It shows the count and opens the full list.
  • Errors turn the label red. The resource with the error can't be selected, and full release turns off, so everything else can still ship.
Goal #04 · Where it's going

The environment stays in view from the first click to Release

Why this design
  • The old dialog named the environment once, in small text, and some people caught themselves in the wrong one mid-release.
  • The environment card shows the cloud, name, status and stage, and sits at the top of both steps, so it's on screen the moment you press Release.
