Cutting daily clicks by 57% by redesigning Facets' web app around how engineers work

Part of Facets' move to React

Facets is a tool companies use to set up and change the cloud servers and databases their apps run on.

With Facets, developers make these changes themselves, like giving an app more memory, instead of raising a ticket with the DevOps team and waiting. The DevOps team sets Facets up, and developers use its web app every day.

My role
Sole product designer. I led the research and designed every screen, and coded parts of the web app. Two frontend engineers built most of it.
Team

TL;DR
Situation

Facets was rebuilding its web app in React, while two older versions still ran side by side.Customers had pushed back on an earlier redesign. If this one failed too, Facets would be running three versions.

Problem

The navigation didn't match how people work.Developers work inside projects, but every screen showed them the organisation's setup tools and crammed their own pages into a row at the top. The most common daily task took 14 clicks.

What I did

I designed the navigation around the two kinds of users first, then rebuilt every screen on it.A side menu for each level, a breadcrumb that switches environment in one click, and one header that shows status and actions. The team had tried breadcrumbs before, so I proved it first: a working build, tests with users, and a two-phase rollout.

Result

57% fewer clicks on the most common daily task, and satisfaction up from 5.8 to 8.4.Every customer moved to the new web app, and both older versions were switched off.

How it evolved

I rebuilt the navigation first, because it would make or break the redesign

A smaller fix would have been cheaper. But the confusion came from the navigation itself, and every other screen is built on it.

Every page's links and redirects would change. It was the biggest change in the redesign, and the only option that fixed the cause.

I mapped the whole web app first: every level, every page, and what each page has to show. Two principles came out of it:

The redesign

Three parts that work together: the side menu, the breadcrumb and the header

Facets has four levels, dozens of pages and up to twelve actions on one environment. Each part of the navigation answers one question, in the same place on every screen.

1 · Side menu

Which level am I at?

The organisation's menu outside a project, the project's menu inside one.

2 · Breadcrumb

Where exactly am I?

Project, environment and page. Each step is a menu, so you can switch environment or page in one click.

3 · Header

What is this, and what can I do?

The environment or resource you're on, its state, and the action you need now.

Goal #01 · Where am I

The side menu changes with the level, so the menu itself tells you where you are

3.4 → 1.1 back-and-forth page visits to reach a task
Why this design
  • Platform engineers find the organisation's setup outside projects. Developers inside a project see only that project's pages. The two never mix, so the menu always shows which level you're at.
  • The project's pages moved out of the crowded row at the top and into the side menu, which had room for them.
  • Environments, the item people use most, opens a list of every environment and its pages, so you can go straight to a page in any of them.
Goal #02 · Environment work

Releases, resources and secrets went back inside the environment

  1. Every page of this environment, one click away

Before: Resource Center was a project tab. You picked the environment inside the page, and the breadcrumb never said which one you were in.

Fewer clicks for everyday work inside an environmentGood feedback on the new navigation
Why this design
  • Each environment has its own pages again: Resource Center, Secrets & Variables, Releases, Monitoring & Alerts and more. Going into an environment takes you to its work.
  • Secrets & Variables also stays at the project level, for comparing environments side by side. That was the one job the earlier redesign had right.
Goal #03 · Switching

Changing environment is one click, and you stay on the same page

  1. Pick another environment. You stay on Resource Center
  1. Any page of any environment, from the side menu

Before: a panel with up to three lists and Apply. The earlier redesign added a second switcher with its own Apply.

Why this design
  • People switch environments all the time, usually to check the same thing somewhere else, so the switch keeps you on the same page.
  • The original UI already kept your page when you switched. The panel, the extra lists and the Apply button made it slow, so I kept the behaviour and removed the form.
Goal #04 · Common actions

Project Overview puts common actions one click from the project

  1. Resource Actions: pick a resource, then edit its settings, override it or release it
  2. Environment Actions: pick an environment, launch or release it, or open one of its pages

Before: the project opened on a list of environments.

Main way to navigate for advanced users61% of visits to Project Overview go straight to an action
Why this design
  • Advanced users were hunting through the navigation for routine actions, so I proposed a page that puts them up front: pick a resource or an environment and act on it.
  • It came after the environment pages on purpose. A shortcut only helps if it opens a complete page, and the earlier redesign had shortcuts without the pages.
Goal #05 · The same everywhere

One header for projects, environments and resources

The hardest component in the web app. One design had to handle:

3 kinds of object

Projects, environments and resources

A state that changes

Running, stopped, launching, failed

Up to 12 actions

On a single environment

Before: each page had only some of the actions

  1. Only release actions here
  2. Everything else: only in this panel

On Releases you got release actions. For anything else, like credentials or the VPN profile, you had to go to Environments and open the environment. People did this all the time, and it showed up in support tickets. The original UI split actions across pages the same way.

Now: every action sits in the environment's header, on every one of its pages.

1 · Icon

The cloud for an environment, the resource type for a resource

2 · Name

The project, environment or resource you're on

3 · Status and context

State, stage, region, and whether it depends on another environment

4 · Actions

The one you need now, and everything else under More
